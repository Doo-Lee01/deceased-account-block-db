## 2. 배경과 범위

### 왜 이 제도가 생겼나

기존에는 행정안전부의 사망자 정보가 **월 1회**, 그것도 일부 금융회사에만 제공되었습니다. 사망신고 기한 1개월과 합쳐지면 은행이 사망 사실을 알기까지 **최대 2개월**의 공백이 생깁니다. 그 사이 사망자 명의 계좌에서 인출과 이체가 계속 가능해 상속인 간 분쟁과 명의도용 범죄의 통로가 되었습니다.

개선 후에는 정보가 **매일 1회** 전 금융권에 제공되고, 사망신고 접수 **다음 날**부터 입금을 제외한 모든 거래가 차단됩니다.

### 제도를 DB 요구사항으로

| 제도 내용 | 모델에 반영한 것 |
|---|---|
| 매일 1회 정보 수신 | 파일 단위 + 레코드 단위 수신 이력 |
| 사망신고 다음 날부터 차단 | 차단개시일시 = 사망일이 아니라 신고일 + 1일 |
| 입금 등 필수 거래만 허용 | 거래유형 × 방향을 **데이터로** 관리하는 규칙 테이블 |
| 치료비·장례비 예외 인출 | 신청–서류–승인–지급 상태 흐름 + 지정 수취처 |
| 자동이체 중단 | 약정과 처리결과 분리, 실패사유코드 기록 |
| 처리 이력의 전자적 기록·관리 | 감사로그 — 사망정보 **조회** 이력까지 포함 |

### 구현 범위

**범위 내** — 은행 1개사 · 입출금이 자유로운 예금 1종.
사망정보 수신 → 고객·계좌 상태 반영 → 거래 차단 판정 → 예외 인출 → 감사·집계

**범위 외**

| 제외 | 사유 |
|---|---|
| 카드·보험·증권 | 업권별 원장 구조가 상이해 모델 규모가 과도해짐 |
| 상속 분할·상속세 | 금융회사 시스템 밖의 업무(법원·세무) |
| 대출 원장 | 차단 대상 거래유형으로만 정의 |
| 금융공동망 고정길이 전문 | 참가기관 대상 비공개 규격 |
| 실제 행정안전부 API | 실습 환경에서 접근 불가. 샘플 파일 적재로 대체 |
| 화면·인증 | DB 과목 범위 밖. 채널계는 요청/응답 로그로만 표현 |

### 가정

| No | 가정 | 영향 |
|---|---|---|
| A-01 | 제공 정보에 사망일자와 **사망신고일자**가 모두 포함된다 | 차단개시일시 산출의 전제. 틀리면 제도가 성립하지 않음 |
| A-02 | 원천에 실명확인번호가 있으면 이를 우선 매칭 키로 쓰고, 없거나 매칭되지 않으면 성명·생년월일로 후보를 만든다 | 다건매칭 가능성 → 자동 차단하지 않고 수작업 확인 대상으로 분리 |
| A-03 | 차단은 **고객 단위**로 설정되고 보유 계좌 전체에 전파된다 | 차단 마스터의 주키가 계좌가 아닌 고객번호 |

## 3. 아키텍처

실제 은행은 역할에 따라 시스템을 나눕니다. 그 구조를 하나의 MySQL 서버 안에서 **데이터베이스(스키마)를 나누는 방식**으로 재현했습니다.

| 스키마 | 계층 | 역할 | 테이블 |
|---|---|---|---|
| `ext_link` | 대외계 | 행정안전부·한국신용정보원 수신 데이터를 가공 없이 보관 | 3 |
| `core_bank` | 계정계 | 고객·계좌·거래원장. 잔액을 실제로 움직이는 원장 | 15 |
| `channel` | 채널계 | 창구·ATM 요청을 받아 계정계에 전달하고 결과를 반환 | 3 |
| `info_mart` | 정보계 | 영업 종료 후 일배치 집계 및 감사 이력 관리. 집계 테이블은 고객 식별정보를 직접 보관하지 않음 | 4 |
| `comm_code` | 공통 | 네 계층이 모두 참조하는 코드·응답문구·영업일 | 5 |

데이터가 흐르는 방향은 두 갈래입니다.

- **외부 → 대외계 → 계정계** — 사망정보가 들어와 차단이 생기는 경로
- **고객 → 채널계 → 계정계 → 정보계** — 거래가 처리되고 집계되는 경로

### 나눈 이유가 곧 설계 결정

통계 쿼리가 원장을 직접 대량 스캔하면 거래 처리와 분석 조회가 같은 자원을 두고 경쟁할 수 있습니다. 대외계 원천을 재적재하거나 정리하는 작업이 계정계 데이터와 강하게 결합되면 운영이 어려워집니다. 채널계가 계정계와 FK로 묶이면 존재하지 않는 계좌번호로 온 요청을 저장할 수 없어 추적이 불가능해집니다.

그래서 계층 내부는 FK로 묶고, 계층 사이는 값만 전달하는 구조로 잡았습니다.

### 데이터가 쌓이는 순서

각 단계에서 어느 테이블에 행이 생기는지가 곧 그 테이블이 존재하는 이유입니다.

| | 일어나는 일 | 행이 생기는 곳 |
|---|---|---|
| 1 | 새벽 1시, 사망자 파일 수신 | `ext_death_file` `ext_death_record` |
| 2 | 해시로 고객 매칭 | `ext_death_record.match_status_cd` 갱신 |
| 3 | 차단 생성 (신고일+1일 00:00 산출) | `death_block` `death_block_hist` `cust_status_hist` `acct_status_hist` |
| 4 | 사망정보를 조회했다는 사실 | `audit_death_access` |
| 5 | ATM 출금 시도 → 차단 | `chnl_request` `chnl_block_decision` `chnl_response` |
| 6 | 타행에서 입금 → 허용 | `acct_txn` · `acct.balance_amt` 갱신 |
| 7 | 자동이체일 도래 → 실패 | `auto_transfer_result` |
| 8 | 유가족이 장례비 신청 | `exc_request` → `exc_document` → `exc_approval` → `exc_payout` + `acct_txn` |
| 9 | 오매칭 판명 → 차단 해제 | `death_block` 갱신 · `death_block_hist` · `cust_status_hist` |
| 10 | 영업 종료 후 야간 집계 | `stat_block_daily` `stat_exception_daily` `stat_mismatch` |

거래 처리 중 **참조만** 하는 테이블 — `block_rule` `payee_registry` `code_detail` `rsp_code` `org_code` `biz_calendar`

### 거래 한 건의 처리

출금 요청이 들어오면 **세 곳을 읽어** 판정하고 **네 곳에 기록**합니다.

| | 대상 | 하는 일 |
|---|---|---|
| 읽기 1 | `acct` | 예금주와 잔액 확인 |
| 읽기 2 | `death_block` | 차단중인가, 개시일시를 지났는가 |
| 읽기 3 | `block_rule` | 이 거래유형은 허용인가 |
| 쓰기 1 | `chnl_block_decision` | 판정 결과 — **허용도 기록** |
| 쓰기 2 | `acct_txn` | 허용일 때만 기표 |
| 쓰기 3 | `acct.balance_amt` | 허용일 때만 갱신 |
| 쓰기 4 | `audit_death_access` | 조회했다는 사실 기록 |

차단 정보가 없으면 규칙은 조회하지 않습니다. 차단된 거래는 원장에 남지 않고 판정이력과 감사로그에만 남습니다.

## 4. 설계 의사결정

### ① 차단 기준일은 사망일이 아니다

가족관계등록법 제84조는 사망신고에 일정한 기간을 두고 있습니다. 그래서 사망일과 신고일 사이에 시차가 생기고, 은행은 신고가 접수되어야 사망 사실을 알 수 있습니다. 사망일을 기준으로 차단하면 이미 처리된 거래를 소급해 막는 셈이 됩니다.

차단개시일을 신고일 다음 날로 잡은 것은 법조문이 아니라 대상 제도의 업무규칙에서 가져온 것입니다. 모델에는 이 규칙을 제약으로 못박았습니다.

```sql
CONSTRAINT ck_block_start CHECK (
  block_start_dtm = TIMESTAMP(DATE_ADD(death_report_dt, INTERVAL 1 DAY))
)
```

계산 결과를 컬럼에 저장한 이유는 두 가지입니다. 조회할 때 함수를 씌우면 **인덱스를 타지 못하고**, 원천이 정정되면 **과거 판정의 근거까지 소급해 바뀌기** 때문입니다.

### ② 업무 규칙을 코드가 아닌 데이터로

"입금만 허용"을 `IF`문으로 하드코딩하면 규정이 바뀔 때 코드를 고치고 재배포해야 합니다. `block_rule` 테이블로 분리해, 규칙이 바뀌면 기존 행의 적용기간을 종료하고 새 규칙 행을 추가하는 방식으로 대응합니다. 규칙 데이터만 바뀌는 경우에는 애플리케이션 코드를 고치지 않아도 됩니다.

| 거래유형 | 방향 | 허용 | 예외인출 | 응답코드 |
|---|---|---|---|---|
| DEP 입금 | I | Y | — | — |
| TRI 이체입금 | I | Y | — | — |
| WDR 출금 | O | N | 가능 | D001 |
| TRO 이체출금 | O | N | 가능 | D001 |
| ATO 자동이체 | O | N | 불가 | D002 |
| CLS 계좌해지 | O | N | 불가 | D003 |
| LON 대출실행 | O | N | 불가 | D004 |

기존 행을 덮어쓰지 않고 `apply_to_dt`로 종료일을 끊는 이유는 과거 판정의 근거를 남기기 위해서입니다. 이력 테이블과 같은 방식입니다.

규칙 자체의 무결성도 제약으로 지킵니다.

```sql
CONSTRAINT ck_rule_rsp_req CHECK (
  (allow_yn = 'Y' AND reject_rsp_cd IS NULL) OR
  (allow_yn = 'N' AND reject_rsp_cd IS NOT NULL)
)
```

**허용 규칙에는 거절코드를 둘 수 없고, 차단 규칙에는 반드시 거절코드가 있어야 합니다.** `allow_yn`과 `reject_rsp_cd`의 조합이 업무 의미와 어긋나면 DB가 저장을 거부합니다.

이 제약이 없다면 두 가지 모순이 데이터에 들어올 수 있습니다. 허용 규칙에 거절코드가 붙으면 거래는 승인하면서 고객에게는 거절 메시지를 내보내게 되고, 차단 규칙에 거절코드가 없으면 거래를 막고도 이유를 알려줄 수 없습니다.

### ③ 정책을 애플리케이션이 아니라 스키마로

지켜야 할 정책은 하나입니다. **예외인출 대금은 등록된 병원·장례식장으로만 나간다.**

보통은 애플리케이션 코드로 막지만, DB에 들어오는 경로는 하나가 아닙니다.

| 경로 | 검증 코드를 거치나 |
|---|---|
| 창구 애플리케이션 | 거침 |
| 야간 배치 프로그램 | 다른 팀이 만듦 |
| 운영자의 DB 콘솔 | 코드를 안 거침 |
| 데이터 이관 스크립트 | 일회성이라 검증 생략 |

```sql
payee_id BIGINT NOT NULL,
CONSTRAINT fk_expay_payee FOREIGN KEY (payee_id)
  REFERENCES payee_registry (payee_id)
```

`NOT NULL`과 `FOREIGN KEY`를 함께 걸어야 합니다. NULL은 FK 검사를 통과하기 때문입니다. 이렇게 두면 어느 경로로 들어오든 DB가 거절하고, 등록되지 않은 계좌번호가 들어갈 자리 자체가 없습니다.

### ④ FK를 걸지 않은 논리 참조 8개

다른 테이블의 값을 담지만 **의도적으로 FK를 걸지 않은 컬럼**이 8개 있습니다. 사유는 세 가지입니다.

**원천의 독립성** — 대외계 데이터를 재적재하거나 정리할 때 계정계가 막히면 안 됩니다.

| 컬럼 | 가리키는 곳 |
|---|---|
| `ext_death_record.matched_cust_no` | `cust.cust_no` |
| `death_block.source_record_id` | `ext_death_record.death_record_id` |

**존재하지 않는 값도 기록되어야 함** — FK를 걸면 잘못된 값이 들어온 요청 자체가 저장되지 않아 추적할 수 없습니다.

| 컬럼 | 가리키는 곳 | 이유 |
|---|---|---|
| `chnl_request.cust_no` | `cust.cust_no` | 없는 고객번호로 온 요청도 기록 |
| `chnl_request.acct_no` | `acct.acct_no` | 없는 계좌번호로 온 요청도 기록 — 공격 시도 추적 |
| `ext_inquiry_log.target_cust_no` | `cust.cust_no` | 대외 조회 이력은 대상과 무관하게 보존 |
| `audit_death_access.target_cust_no` | `cust.cust_no` | 감사로그는 대상이 사라져도 남아야 함 |

**판정 시점의 스냅샷** — 참조 대상이 폐기되거나 정정돼도 당시 판정 근거는 보존되어야 합니다.

| 컬럼 | 가리키는 곳 | 이유 |
|---|---|---|
| `chnl_block_decision.applied_rule_id` | `block_rule.rule_id` | 규칙이 폐기돼도 과거 판정 이력은 남음 |
| `chnl_block_decision.txn_unique_no` | `acct_txn.txn_unique_no` | 판정 결과는 원장과 독립적으로 보존 |

나머지 관계는 모두 FK로 묶었습니다. 같은 성격의 컬럼을 다르게 처리하지 않도록, `auto_transfer_result.txn_unique_no`에도 `exc_payout.txn_unique_no`와 동일하게 FK를 설정했습니다.

### ⑤ 이력 현재행을 센티널 날짜로 관리

상태가 바뀔 때마다 기존 행을 남기고 새 행을 추가하는 SCD Type 2 방식입니다.

```sql
valid_to_dtm DATETIME(3) NOT NULL DEFAULT '9999-12-31 23:59:59.999',
UNIQUE KEY uk_cust_hist_current (cust_no, valid_to_dtm)
```

NULL 대신 센티널 값을 쓴 이유는 UNIQUE 제약 때문입니다. MySQL의 UNIQUE는 NULL을 서로 다른 값으로 취급해 `(고객A, NULL)` 행이 여러 개여도 막지 않습니다. 실제 값을 넣어야 현재행이 하나임을 DB가 보장할 수 있습니다.

> **운영 주의** — 새 상태를 넣기 전에 기존 현재행을 먼저 닫아야 합니다.
> ```sql
> UPDATE cust_status_hist SET valid_to_dtm = NOW(3)
>  WHERE cust_no = ? AND valid_to_dtm = '9999-12-31 23:59:59.999';
> INSERT INTO cust_status_hist (...) VALUES (...);
> ```
> 순서를 바꾸면 UNIQUE 위반이 납니다. 이것이 정상 동작입니다.

`close_dt`처럼 "구간의 끝"이 아니라 "사건의 발생 여부"를 뜻하는 컬럼은 NULL이 맞습니다. 센티널을 넣으면 평균 존속기간 같은 집계가 왜곡됩니다.

### ⑥ 복합키 코드표에 외래키 걸기

`code_detail`의 기본키는 `(group_cd, code_cd)`입니다. `10`이라는 코드값이 고객상태 그룹에도 예외인출사유 그룹에도 있어 코드값만으로는 유일하지 않기 때문입니다. 그런데 `cust`에는 `group_cd`가 없어 FK를 걸 수 없습니다.

```sql
cust_status_cd  CHAR(4) NOT NULL,
cust_status_grp CHAR(10) GENERATED ALWAYS AS ('CUST_ST') STORED,

CONSTRAINT fk_cust_status FOREIGN KEY (cust_status_grp, cust_status_cd)
  REFERENCES comm_code.code_detail (group_cd, code_cd)
```

`cust_status_grp`는 항상 `'CUST_ST'`가 되는 생성컬럼입니다. MySQL이 자동으로 채우므로 `INSERT`에 쓰지 않습니다.

**얻은 것** — 존재하는 코드인지뿐 아니라 **이 컬럼에 맞는 그룹의 코드인지**까지 막습니다. 고객상태 컬럼에 예외인출 상태값 `REQ`를 넣으면 거부됩니다.
**지불한 비용** — 생성컬럼 35개, FK마다 인덱스 자동 생성, `CASCADE` 사용 불가.

### ⑦ 규제 요건을 컬럼으로

| 법령 요건 | 반영 |
|---|---|
| 개인정보보호법 제24조의2 | `rrn_hash CHAR(64)` 검색용 + `rrn_enc VARBINARY(128)` 저장용 **분리** |
| 전자금융거래법 제22조·시행령 제12조 | 거래기록 보존 요건을 검토해 거래 추적에 필요한 컬럼(`terminal_id` 등)과 보존 구조를 설계 |
| 신용정보법 제20조의2 | `cust.close_dt` — 보존기간 5년의 기산점 |

매칭에는 동일한 입력을 동일하게 비교할 수 있는 일방향 변환값을 쓰고, 원문 복원이 필요한 경우를 대비해 암호문을 별도로 보관하는 구조로 분리했습니다. 이 프로젝트에서는 `rrn_hash`와 `rrn_enc` 두 컬럼으로 표현했습니다.

실제 운영 환경이라면 키 관리와 접근통제를 포함한 개인정보 보호 설계가 별도로 필요합니다. 여기서는 컬럼을 분리한다는 구조만 다뤘습니다.

**채택하지 않은 것 — 연 단위 파티셔닝.** 보존연한 관리에는 유리하지만 MySQL InnoDB는 파티션 테이블에 FK를 걸 수 없습니다.

```
ERROR 1506 (HY000): Foreign keys are not yet supported in conjunction with partitioning
```

거래원장에 FK가 5개 걸려 있어 파티셔닝을 택하면 참조 무결성을 전부 포기해야 합니다. **참조 무결성을 택하고** 보존기간 관리는 아카이브 테이블 이관으로 대체했습니다.

### ⑧ 삭제는 전부 RESTRICT

`ON DELETE CASCADE`를 쓰지 않았습니다. 금융 데이터는 지우는 것이 아니라 상태를 바꾸는 것이고, 실수로 고객 한 명을 지웠을 때 거래원장까지 연쇄 삭제되면 복구가 불가능합니다.

## 5. 정규화

**3NF를 기준으로 설계**했습니다. 테이블별 함수 종속 점검 결과는 [발표 자료 부록 A1](https://Doo-Lee01.github.io/deceased-account-block-db/presentation.html)에 정리했습니다.

| 단계 | 제거 대상 | 실제로 한 일 |
|---|---|---|
| 1NF | 다중값·반복 속성 | 증빙서류를 `exc_document`로, 승인을 `exc_approval`로 분리해 한 건당 한 행 |
| 2NF | 부분 함수 종속 | 복합키를 쓰는 `code_detail`에서 비키 속성이 전체 키에 종속되도록 설계 |
| 3NF | 이행 함수 종속 | 기관명·코드명·응답메시지를 원장에 두지 않고 **코드만 저장**해 조인 |

30개 테이블 중 12개는 데이터 중복과 다중값 속성, 이력 관리, 코드 관리를 분리하는 과정에서 별도 엔터티로 구성한 것입니다. 이력 3종, 예외인출 4종, 코드 5종.

### 의도적 반정규화 3건

이유는 두 가지뿐입니다. **조회 성능**과 **판정 시점의 값 고정**.

| 컬럼 | 이유 | 내용 | 대가 |
|---|---|---|---|
| `acct.balance_amt` | 성능 | 거래원장 합계로 구할 수 있으나 20년치가 쌓이면 잔액 조회 한 번에 수만 행을 훑어야 함 | 잔액–원장 대사 쿼리 필요 |
| `acct_txn.balance_after_amt` | 시점 | 그 거래 직후의 잔액을 재계산 없이 답하기 위해. 오픈뱅킹 거래내역조회 API 응답 필드와도 일치 | 원장 수정 시 재계산 |
| `death_block.death_report_dt` | 시점 | 원천이 정정·재전송돼도 판정에 실제로 쓴 값은 바뀌면 안 됨 | 원천과 불일치 가능 |

**판단 기준** — 아래를 모두 만족할 때만 허용했습니다.
① 조회가 쓰기보다 훨씬 잦은가 ② 재계산 비용이 데이터 증가에 비례하는가 ③ 어긋남을 검증할 방법이 있는가

> 반정규화의 목적은 성능과 시점 고정이고, 대사 쿼리는 그 결과로 생긴 비용입니다. 중복을 만들었기 때문에 어긋날 가능성이 생겼고 이를 확인할 방법이 필요해졌습니다.
>
> `payee_id`가 `exc_request`와 `exc_payout` 양쪽에 있는 것은 반정규화가 아닙니다. 하나는 신청 시 지정한 수취처, 다른 하나는 실제 지급한 수취처로 의미가 다른 별개 컬럼입니다.

**S2 — 경계값**

|---|---|---|---|
| 2026-09-12 23:59:00 | 차단개시 전 | 허용 | `0000` |
| 2026-09-13 00:00:01 | 차단개시 후 | 차단 | `D001` |

**S4 — 판정 시뮬레이션.** 분기문 없이 `block_rule` 조인만으로 7개 케이스의 판정 결과가 나옵니다.

```sql
CASE
 WHEN b.cust_no IS NULL OR b.block_status_cd <> '20'
      THEN '허용 (차단 없음)'
 WHEN x.txn_dtm < b.block_start_dtm
      THEN '허용 (차단개시 전)'
 WHEN r.allow_yn = 'Y'
      THEN '허용 (규칙상 필수거래)'
 ELSE CONCAT('차단 (', r.reject_rsp_cd, ')')
END
```

**S9~S11 — 무결성 3종.** 잔액과 원장 합계가 5개 계좌 전부 일치, 이력 현재행이 고객당 정확히 1건, 유효구간에 단절·중복 없음.

유효구간에 틈이 있으면 그 시점의 상태를 알 수 없고, 겹치면 상태가 둘이 됩니다. 두 경우가 모두 없어야 임의의 시점에 대한 상태 조회가 한 건만 반환합니다.

## 8. 법령 근거

조문 원문과 검토 과정은 **[노션 페이지](https://rhinestone-crafter-09e.notion.site/HOME-3dd49d7e6ffa805db933ff0284e0e2db?source=copy_link)** 에 정리했습니다. 아래는 모델에 반영된 결과만 요약한 것입니다.

> 아래 내용은 데이터 모델을 도출하기 위해 검토한 **학습 목적의 정리**이며, 실제 금융기관의 법률·컴플라이언스 판단을 대체하지 않습니다. 조문 해석에 오류가 있을 수 있습니다.

| 축 | 근거 법령 | 모델 반영 |
|---|---|---|
| 기준정보 | 가족관계등록법 제84조·제85조 | `death_dt`와 `death_report_dt` 분리, 차단 기준을 신고일+1일로 확정 |
| 개념·논리 | 민법 제997조·제998조의2·제1000~1003조 | 예외인출 엔터티 도출, 신청인 자격을 법정 상속순위로 제한 |
| 물리 스키마 | 전자금융거래법 제22조·시행령 제12조, 개인정보보호법 제24조의2 | 법정 필수 컬럼 배치, 보존연한 확정, 해시·암호문 분리 |
| 업무 규칙 | 금융실명법 제3조·제4조 | 규칙 테이블 분리, 오매칭 권리구제 이력, 수취처 직수령 금지 |
| 검증·감사 | 전자금융감독규정 제13조 | 감사로그에 조회 주체·목적·성공여부 강제 저장 |

조문 검토를 바탕으로 세 가지 **설계 가정**을 세웠고, 그것이 스키마에 직접 반영됐습니다.

**금융실명법 제3조 검토 → 오매칭 복구를 필수 기능으로 설계**
실명이 확인된 계좌의 자산을 명의자 소유로 추정하는 규정을 고려해, 오매칭된 생존 고객의 차단을 되돌릴 수 있어야 한다고 보았습니다. `death_block`에 해제일시와 해제사유를 두고 이력 테이블에 경위를 남기는 구조로 설계했습니다.

**금융실명법 제3조와 상속 관련 법령 검토 → 예외인출 수취처 제한**
상속 절차가 완료되기 전 상속인 개인계좌로 자금이 나가는 것을 막자는 설계 가정을 세웠습니다. `exc_payout.payee_id`를 `payee_registry`를 참조하는 NOT NULL FK로 두어, 사전 등록된 병원·장례식장 외에는 수취처가 될 수 없게 했습니다. 법조문이 이 규칙을 직접 정하고 있지는 않으며, 조문 검토를 바탕으로 세운 프로젝트의 가정입니다.

**전자금융거래법 시행령 제12조 검토 → 보존기간을 행 단위로 판단**
건당 금액에 따라 보존기간이 나뉘는 점을 확인해, 같은 테이블 안에서도 행마다 파기 시점이 다를 수 있다고 보았습니다. 일괄 삭제 대신 금액 조건을 포함한 아카이브 이관 방식을 전제로 설계했습니다.

## 10. 한계와 다음 단계

### 설계의 전제

행정안전부 제공 정보에 **사망신고일자가 포함된다**고 가정했습니다. 실제 규격을 확인할 수 없었고, 이 가정이 틀리면 제도 자체가 성립하지 않습니다.

### 매칭의 한계

해시 기반 매칭은 동명이인을 구분하지만, 원천에 주민번호가 없으면 성명·생년월일로 다건매칭이 발생합니다. 잘못 차단하면 생존 고객의 금융거래가 막히므로 자동 차단하지 않고 `match_status_cd = '40'`으로 분리해 수작업 확인 대상으로 둡니다.

### 동시성

스키마 설계 범위라 트랜잭션 제어는 구현하지 않았습니다. 다만 동시 거래에서 생기는 문제를 재현하고 해결 순서를 검증해 [`concurrency/`](concurrency/)에 정리했습니다. 원리와 터미널 흐름은 [실습 보고서](https://Doo-Lee01.github.io/deceased-account-block-db/lock-lab-report.html)에서 슬라이드로 볼 수 있습니다.

`acct_txn.acct_no`의 FK는 원장 기록 시 계좌 행에 공유락을 겁니다. 그래서 "원장 기록 → 잔액 변경" 순서로 두 거래가 같은 계좌를 처리하면 데드락이 납니다. 계좌를 `SELECT … FOR UPDATE`로 먼저 잠그면 해소되고, 이때도 일반 조회는 기다리지 않습니다. 이 해결은 트랜잭션 작성 방식의 문제라 `schema.sql`은 바꾸지 않았습니다.

### 다음 단계

- 배치 프로시저 — 사망정보 매칭에서 차단 생성까지
- 판정 로직을 Java 서비스 계층으로 이관 — `FOR UPDATE`와 데드락 재시도 포함
- 로그 보존기간 확정과 아카이브 이관 설계

판정 로직을 프로시저에 몰아넣지 않았습니다. 규칙은 테이블에 두고 조합과 분기는 서비스 계층에 두는 구조라, Java로 옮길 때 DB 쪽을 거의 건드리지 않아도 됩니다.
