# 락 · 데드락 시연

같은 계좌에 두 거래가 동시에 들어올 때 생기는 문제와 해결 방법을 세 개의 터미널(A · B · OBS)로 재현합니다.

| 시나리오 | 파일 | 결과 |
|---|---|---|
| 1. 데드락 발생 | `01_deadlock.sql` | B가 `ERROR 1213`으로 취소됨 |
| 2. 데드락 해결 | `02_deadlock_fixed.sql` | 두 입금이 차례로 처리됨 |
| 3. 출금 갱신 분실 | `03_lost_update.sql` | 70만원이 사라짐 / CHECK가 막음 |
| 4. 출금 문제 해결 | `04_withdraw_fixed.sql` | 한 명 승인, 한 명 거절 |
| 5. 잠겨 있어도 조회는 된다 | `05_read_while_locked.sql` | 일반 SELECT는 기다리지 않음 |

MySQL 8.0.46에서 다섯 시나리오를 단계별로 실행해 각 파일의 기대 결과와 일치하는 것을 확인했습니다.

---

## 1. 무엇이 문제인가

### 데드락

README 3장에 적은 거래 처리 순서는 이렇습니다.

```
① 거래원장(acct_txn)에 기록  →  ② 계좌(acct) 잔액 변경
```

`acct_txn.acct_no`에는 계좌 테이블을 가리키는 FK가 있습니다. 그래서 ①에서 MySQL이 계좌가 실제로 있는지 확인하면서 **계좌 행에 S 락(읽는 중)** 을 자동으로 붙입니다. 이 락은 COMMIT 전까지 풀리지 않습니다.

두 세션이 같은 계좌에 동시에 입금하면,

```
A: ① 원장 기록 → 계좌에 S 락
B: ① 원장 기록 → 계좌에 S 락      (S 끼리는 공존 가능)
A: ② 잔액 변경 → X 락 필요 → B 의 S 때문에 대기
B: ② 잔액 변경 → X 락 필요 → A 의 S 때문에 대기   → 데드락
```

MySQL이 이를 감지해 한쪽을 취소합니다.

### 갱신 분실

출금은 잔액이 충분한지 먼저 봐야 합니다. 잔액을 잠그지 않고 읽으면 두 세션이 같은 값을 보고 각자 판단합니다.

```
A: 잔액 100만 읽음 → 70만 출금 가능
B: 잔액 100만 읽음 → 70만 출금 가능
A: 잔액을 30만으로 저장
B: 잔액을 30만으로 저장           → 140만이 나갔는데 30만 남음
```

에러가 나지 않고 틀린 값이 저장되기 때문에 데드락보다 위험합니다.

## 2. 해결 방법

### 원칙 1 — 고칠 행은 처음부터 X 락으로 잡는다

```sql
BEGIN;
SELECT balance_amt INTO @bal
  FROM acct WHERE acct_no = ?
   FOR UPDATE;                    -- 읽는 순간 X 락
-- 판단
UPDATE acct SET balance_amt = balance_amt - ? WHERE acct_no = ?;
INSERT INTO acct_txn (...) VALUES (...);
COMMIT;
```

`FOR UPDATE`는 "곧 고칠 것"이라는 선언입니다. 먼저 온 세션이 X 락을 쥐면 뒤에 온 세션은 **아무 락도 쥐지 못한 채** 맨 앞에서 기다립니다. 서로 붙잡고 기다리는 상황이 생기지 않습니다.

두 문제가 이 한 줄로 함께 해결됩니다.

| 문제 | 해결되는 이유 |
|---|---|
| 데드락 | S 를 쥔 채로 X 로 바꾸려는 단계가 없어짐 |
| 갱신 분실 | 뒤의 세션이 앞의 세션이 끝난 뒤의 잔액을 읽음 |

### FOR UPDATE를 쓰면 조회도 막히지 않나

막히지 않습니다. 일반 `SELECT`는 락을 요청하지 않습니다. InnoDB는 행을 바꿀 때 이전 값을 따로 보관해 두고, 일반 `SELECT`에는 그 보관본에서 **마지막으로 커밋된 값**을 돌려줍니다(MVCC). 기다리는 것은 `FOR SHARE` · `FOR UPDATE` · `UPDATE`처럼 스스로 락을 요청한 문장뿐입니다.

| 문장 | 락 요청 | 남이 X 락 중일 때 |
|---|---|---|
| `SELECT` | 없음 | 바로 나옴 · 커밋된 값 |
| `SELECT … FOR SHARE` | S | 기다림 |
| `SELECT … FOR UPDATE` | X | 기다림 |
| `UPDATE` · `DELETE` | X | 기다림 |

조회만 할지, 조회 후 변경할지는 DB가 알아내지 않습니다. **개발자가 어떤 문장을 쓰느냐로 정합니다.** 잔액 조회 화면은 `SELECT`, 출금 처리는 `SELECT … FOR UPDATE`. 반대로 조회만 하면서 `FOR UPDATE`를 쓰면 그 계좌의 다른 거래를 불필요하게 줄 세우게 되므로 피해야 합니다.

시나리오 5에서 확인할 수 있습니다.

### 원칙 2 — 잔액 변경은 DB에서 계산한다

```sql
-- 피할 것
UPDATE acct SET balance_amt = 300000 WHERE ...;               -- 앱이 계산한 값

-- 쓸 것
UPDATE acct SET balance_amt = balance_amt - 700000 WHERE ...;  -- 현재 값 기준
```

현재 값에서 계산하면 적어도 다른 세션의 변경을 덮어쓰지는 않습니다. 이 경우 `ck_acct_balance`가 마이너스 잔액을 막아 줍니다(시나리오 3 PART B). 다만 이것만으로는 "승인 판단 후 실패"가 남으므로 원칙 1과 함께 써야 합니다.

### 원칙 3 — 한 거래는 하나의 트랜잭션으로 묶는다

잔액 변경과 원장 기록을 `BEGIN … COMMIT`으로 묶지 않으면 중간에 실패했을 때 한쪽만 반영됩니다.

### 원칙 4 — 락을 잡는 순서를 통일한다

여러 행을 잠가야 한다면 모든 코드에서 **같은 순서**로 잡습니다. 이 프로젝트에서는 "계좌 → 원장" 순서입니다. 계좌 이체처럼 두 계좌를 잠글 때는 계좌번호가 작은 쪽부터 잡는 식으로 규칙을 정합니다.

### 원칙 5 — 데드락이 나면 재시도한다

순서를 지켜도 데드락이 완전히 사라지지는 않습니다. `ERROR 1213`(SQLSTATE `40001`)은 **재시도해도 되는 오류**입니다. MySQL이 한쪽을 통째로 되돌렸으므로 처음부터 다시 실행하면 됩니다. Java 단계에서 이 오류를 잡아 몇 번 재시도하는 로직이 필요합니다.

## 3. 준비 (처음 한 번)

### 3-1. 스키마와 시연 도구 설치

```
schema.sql          (프로젝트 스키마 — 이미 했다면 생략)
00_setup.sql        (시연 도구 · 시연 계좌)
```

Workbench에서 파일을 열고 번개 버튼으로 실행하면 됩니다. `00_setup.sql`이 만드는 것은 다음과 같습니다.

| 이름 | 역할 |
|---|---|
| `lock_lab` 데이터베이스 | 시연 도구를 프로젝트 스키마와 분리해 보관 |
| `lock_lab.iam('A')` | 터미널에 이름표를 붙이고 락 대기 시간을 120초로 설정 |
| `lock_lab.reset()` | 시연 계좌를 잔액 1,000,000원으로 되돌림 |
| `v_locks` `v_waits` `v_trx` `v_acct` | OBS에서 쓰는 관찰용 뷰 |
| 고객 `C8000000001` · 계좌 `10288000000001` | 시연 전용 계좌. 샘플 데이터와 겹치지 않음 |

시연 계좌에는 개설 입금 1건을 함께 넣어서, `reset()` 후에는 `validation_queries.sql`의 잔액 대사가 그대로 통과합니다.

> `schema.sql`을 다시 실행하면 `core_bank`가 새로 만들어져 시연 계좌가 사라집니다. 그때는 `00_setup.sql`도 다시 실행하세요.

### 3-2. 런처 설정

`lock-lab.bat`을 메모장으로 열어 비밀번호를 한 번 수정합니다.

```bat

```

기존 KTX 실습 런처와 거의 같고, 세 가지가 다릅니다.

| 항목 | KTX 런처 | 이 런처 |
|---|---|---|
| 기본 데이터베이스 | `ktx` | `core_bank` |
| 접속 직후 실행 | 문자셋 · 대기시간 설정 | `CALL lock_lab.iam('A')` — 이름표 등록까지 |
| 사전 점검 | DB 존재 여부 | 시연 계좌 · 시연 도구 존재 여부 |

이름표가 등록돼야 OBS 화면에 `conn23` 대신 `A` · `B`로 표시됩니다.

## 4. 시연 진행

### 4-1. 터미널 열기

`lock-lab.bat`을 더블클릭하면 A · B · OBS 세 창이 뜨고 시연 계좌가 초기화됩니다. 창을 나란히 배치하세요.

```
┌──────────┬──────────┐
│    A     │    B     │
├──────────┴──────────┤
│         OBS         │
└─────────────────────┘
```

OBS에서 이름표를 확인합니다.

```sql
SELECT * FROM lock_lab.session_label;
```

A · B · OBS가 보이면 준비가 끝났습니다.

### 4-2. 진행 규칙

각 시나리오 파일은 `[STEP n] ▶ 터미널` 단위로 나뉘어 있습니다.

1. 파일을 편집기로 열어 둡니다
2. `[STEP 0]`부터 순서대로, 표시된 터미널에 블록을 복사해 붙여넣습니다
3. 블록 아래 `-- 기대:` 주석과 화면을 비교합니다

**멈추는 단계가 있습니다.** 해당 STEP 주석에 "멈춤"이라고 적혀 있으면 정상입니다. 그 터미널은 그대로 두고 다음 STEP으로 넘어가세요.

### 4-3. 시나리오별 흐름

**시나리오 5 — 잠겨 있어도 조회는 된다** `05_read_while_locked.sql`

A는 출금 처리 중인 창구, B는 모바일 앱으로 잔액을 보는 고객이라고 생각하면 됩니다.

PART A

| STEP | 터미널 | 할 일 | 화면 |
|---|---|---|---|
| A0 | OBS | 초기화 | |
| A1 | A | `FOR UPDATE` · 30만으로 변경 (커밋 안 함) | Query OK |

A3이 핵심 장면입니다. A가 X 락을 쥐고 있는데도 B의 일반 조회는 기다리지 않고, 확정된 값 100만을 봅니다. A5에서 `v_locks`를 보면 A3 때는 B가 목록에 아예 없었다는 것도 확인됩니다.

PART B (선택)

| STEP | 터미널 | 할 일 | 화면 |
|---|---|---|---|
| B0 | OBS | 초기화 | |
| B1 | B | `BEGIN` 후 조회 | 1,000,000 |
| B2 | A | 출금하고 COMMIT | Query OK |
| B3 | B | 같은 트랜잭션에서 다시 조회 | **여전히 1,000,000** |
| B4 | B | COMMIT 후 조회 | 300,000 |

MySQL 기본 격리 수준(REPEATABLE READ)에서는 트랜잭션 안의 첫 조회 시점이 고정됩니다. 출금 판단에 일반 `SELECT`를 쓰면 안 되는 또 하나의 이유입니다.

## 5. OBS 화면 읽는 법

`obs.sql`에 명령을 모아 두었습니다. 자주 쓰는 세 가지만 정리합니다.

### `v_locks` — 누가 무엇을 쥐고 있나

```
| who | tbl  | kind      | raw_mode      | status  | row_key          |
| A   | acct | X (write) | X,REC_NOT_GAP | GRANTED | '10288000000001' |
| B   | acct | X (write) | X,REC_NOT_GAP | WAITING | '10288000000001' |
```

| 컬럼 | 뜻 |
|---|---|
| `kind` | `S (read)` 읽는 중 · `X (write)` 고치는 중 |
| `raw_mode` | MySQL 원래 표기. `REC_NOT_GAP`은 행 하나만 잠갔다는 뜻 |
| `status` | `GRANTED` 쥐고 있음 · `WAITING` 기다리는 중 |

계좌 행 하나만 보이도록 걸러 두었습니다. 원장 INSERT는 공통코드 행에도 S 락을 잡지만, 그쪽은 아무도 X 락을 요청하지 않아 충돌이 없으므로 표시하지 않습니다.

### `v_waits` — 누가 누구 때문에 기다리나

```
| waiting | wants         | blocked_by | holds         |
| A       | X,REC_NOT_GAP | B          | S,REC_NOT_GAP |
```

"A가 X를 원하는데, B가 S를 쥐고 있어서 못 받는다"로 읽습니다. 비어 있으면 아무도 기다리지 않는 상태입니다.

### `SHOW ENGINE INNODB STATUS\G` — 데드락 기록

출력이 길어서 `LATEST DETECTED DEADLOCK` 부분만 보면 됩니다.

```
*** (1) TRANSACTION:
UPDATE acct SET balance_amt = balance_amt + 10000 WHERE ...
*** (1) HOLDS THE LOCK(S):
... lock mode S locks rec but not gap          ← 쥐고 있던 락
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
... lock_mode X locks rec but not gap          ← 기다리던 락
*** (2) TRANSACTION:
(같은 모양)
*** WE ROLL BACK TRANSACTION (2)               ← 취소된 쪽
```

두 트랜잭션이 모두 S를 쥐고 X를 기다리는 모양이 그대로 보입니다.

---

## 6. 발표에서 쓸 때

시간이 3분 정도라면 시나리오 1과 2만 보여주고, 각각 두 장면에 집중합니다.

| 장면 | 보여줄 것 |
|---|---|
| 시나리오 1 STEP 4 | 같은 행에 S 락이 두 개 — 데드락의 원인 |
| 시나리오 1 STEP 7 | B 화면의 `ERROR 1213` |
| 시나리오 2 STEP 4 | B가 쥔 것 없이 `WAITING` — 차이점 |
| 시나리오 2 STEP 7 | 잔액 1,020,000, 오류 없음 |

시간이 더 있으면 시나리오 3 PART A의 결과(140만원 출금, 30만원 잔액)를 보여주세요. 에러 없이 돈이 사라지는 장면이라 인상이 강합니다.

"FOR UPDATE를 쓰면 조회도 못 하지 않느냐"는 질문이 나오면 시나리오 5 STEP A3을 보여주면 됩니다. 30초면 끝납니다.

설명할 때 한 문장으로 정리하면 이렇습니다.

> FK가 부모 행에 S 락을 걸기 때문에, 원장부터 쓰면 두 세션이 S를 쥔 채 X를 기다리다 데드락이 납니다. 계좌를 `FOR UPDATE`로 먼저 잠그면 뒤의 세션이 아무것도 쥐지 않고 기다리게 되어 해결됩니다.

## 7. 문제 해결

| 증상 | 원인과 조치 |
|---|---|
| 런처가 "lock_lab tools are missing" | `00_setup.sql`을 먼저 실행 |
| 런처가 "demo account is missing" | `schema.sql`을 다시 돌려 시연 계좌가 사라짐. `00_setup.sql` 재실행 |
| OBS에 `A` 대신 `conn23`처럼 표시 | 해당 터미널에서 `CALL lock_lab.iam('A');` |
| `reset()`이 멈춤 | A · B에 끝나지 않은 트랜잭션이 있음. A · B에서 `ROLLBACK;` |
| 멈춘 터미널이 2분 뒤 `ERROR 1205` | 락 대기 시간(120초) 초과. 해당 터미널에서 `ROLLBACK;` 후 STEP 0부터 다시 |
| 시나리오 1에서 B 대신 A가 취소됨 | 드물게 MySQL이 반대쪽을 고를 수 있음. 결과 해석은 같음 |
| 한글이 깨짐 | 창 제목 확인 후 `SELECT @@character_set_client;`가 `utf8mb4`인지 확인 |
| 복사한 블록 일부만 실행됨 | 블록 안의 앞 문장이 멈추면 뒤 문장은 대기열에 쌓임. 풀리면 이어서 실행되니 기다리면 됨 |
