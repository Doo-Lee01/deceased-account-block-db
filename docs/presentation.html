설계 결정 ③

규칙을 코드가 아니라 DB에 새긴다

지켜야 할 정책은 하나입니다. 예외인출 대금은 등록된 병원·장례식장으로만 나간다. 이걸 어디서 막느냐가 문제입니다.

보통은 이렇게 막는다

애플리케이션 코드에서

if (!payeeRepo.exists(payeeId)) {
    throw new Exception("미등록 수취처");
}

문제는 이 코드를 거치지 않는 경로가 존재한다는 것입니다.

DB에 들어오는 경로는 하나가 아니다
창구 애플리케이션검증 코드 있음
야간 배치 프로그램다른 팀이 만듦
운영자의 DB 콘솔코드를 안 거침
데이터 이관 스크립트일회성이라 검증 생략

코드로 막으면 첫 번째 경로만 지켜집니다.

우리가 택한 방법

DB가 직접 거절하게 한다

payee_id BIGINT NOT NULL,

CONSTRAINT fk_expay_payee
  FOREIGN KEY (payee_id)
  REFERENCES payee_registry (payee_id)

NOT NULL — 비워 둘 수 없다
FOREIGN KEY — 등록된 수취처가 아니면 값이 될 수 없다

두 제약이 함께 있어야 합니다. NULL은 FK 검사를 통과하기 때문입니다.

결과

어느 경로로 들어오든 DB 엔진이 트랜잭션을 거절합니다. 상속인 개인계좌 번호가 들어갈 자리 자체가 스키마에 없습니다.

설계 결정 ⑤

이력은 왜 9999-12-31로 닫는가

고객 상태가 바뀔 때마다 기존 행을 남기고 새 행을 추가하는 SCD Type 2 방식을 썼습니다.

valid_to_dtm DATETIME(3) NOT NULL
  DEFAULT '9999-12-31 23:59:59.999',

UNIQUE KEY uk_cust_hist_current
  (cust_no, valid_to_dtm)

현재 유효한 행은 종료일시를 센티널 값으로 채웁니다.

NULL로 두면 안 되는 이유

MySQL의 UNIQUE는 NULL을 서로 다른 값으로 취급해 중복을 허용합니다. NULL이면 "현재 행"이 여러 개여도 막히지 않습니다.

센티널을 쓰면

고객당 현재 행이 정확히 1건임을 DB가 보장합니다. 배치가 두 번 돌아도 안전합니다.

다만 close_dt처럼 "구간의 끝"이 아니라 "사건의 발생 여부"를 뜻하는 컬럼은 NULL이 맞습니다. 센티널을 넣으면 평균 존속기간 같은 집계가 왜곡됩니다.

코드표에 외래키를 걸기까지

문제

기본키가 두 컬럼이라 참조할 수 없다

코드표 CODE_DETAIL의 기본키는 (group_cd, code_cd) 두 컬럼입니다. 10이라는 코드값이 고객상태 그룹에도, 예외인출사유 그룹에도 있어서 코드값만으로는 유일하지 않기 때문입니다.

그런데 CUST 테이블에는 cust_status_cd만 있고 group_cd가 없습니다. 외래키는 부모의 기본키 전체를 가리켜야 하므로 걸 수가 없습니다.

생각해 본 대안

① 코드 그룹마다 테이블을 따로 만든다 → 테이블이 24개 늘어남
② CHECK로만 검증한다 → 코드가 추가될 때마다 제약을 고쳐야 함

해결

고정값 컬럼을 하나 붙인다

cust_status_cd  CHAR(4),
cust_status_grp CHAR(10)
  GENERATED ALWAYS AS ('CUST_ST') STORED,

FOREIGN KEY (cust_status_grp, cust_status_cd)
  REFERENCES code_detail (group_cd, code_cd)

cust_status_grp는 항상 'CUST_ST'가 되는 컬럼입니다. MySQL이 자동으로 채우므로 INSERT에 쓰지 않습니다. 이 컬럼 덕분에 두 컬럼짜리 외래키가 성립합니다.

결과

고객상태 컬럼에 예외인출 상태값 REQ를 넣으면 거부됩니다. 존재하는 코드인지뿐 아니라 이 컬럼에 맞는 그룹의 코드인지까지 막습니다.
